# keiba — JRA重賞 予想フレームワーク

中央競馬（JRA）重賞の予想を、直感でなく**再現可能・監査可能な手順**として運用するためのナレッジベース。評価体系（ベース点×係数＋加算層）・失敗則ゲート（rules_master）・検証ログ（log/）を1つのリポジトリで管理し、Claude（Claude.ai プロジェクト / Claude Code）から参照して使う。

## 設計思想（3行）

1. **予想の価値は工程にある。** 同じ入力から同じ手順で同じ結論が出ること（再現性）と、外れたときに「どこが間違えたか」を特定できること（監査可能性）を的中より優先する。
2. **失敗はルールになる。** 振り返りで見つけた失敗則は `log/rules_master.csv` に登録し、次回以降は予想確定前のルールゲートで機械的にチェックする。
3. **エッジの有無はログが答える。** 印別成績・回収率・ベースライン比較を `log/analyze.py` で集計し、n=10単位で閾値・係数を見直す。

## ライフサイクル（1レースが辿る工程）

レースは以下の順で処理する。この順序は `references/週次運用スケジュール.md` 第2項が正本で、曜日への割付（週パターンA〜D）も同ファイルにある。

```
① #準備 <対象週>        週初1回・レース横断・枠順不要
     └ 対象レース確定／予算宣言／未整備ナレッジの検知（収録はしない）
                ↓ 検知結果を受けて
② #収録 <コース or レース>  レース単位・別チャット・枠順不要
     └ C0〜C6。コース補正表・レース別傾向・血統D節・騎手C節・配当レンジ・脚質の機械認定
                ↓ 枠順確定（土曜分＝木／日曜分＝金）
③ #予想 <レース名>       1レース1チャット・1回のみ
     └ 工程0〜12を1応答で完走 → ログ追記
                ↓ 当日
④ #更新 <レース名>       最大2回（当日朝／締切前）・再評価範囲ロック
     └ 馬場・オッズ・馬体重の反映 → ゲート②再チェック → 買い目確定 → 購入
                ↓ 発走・結果確定
⑤ 結果追記              着順・配当・通過順・馬場をJRA公式で確認して結果欄へ（フレーズなし）
                ↓ 原則レース翌日〜月曜
⑥ #振り返り <レース名>    V0〜V7＋rule_fires の outcome 確定・較正カウンタ報告
     └ V6.5で reflection/<日付>_<レース名>.md を出力（1レース1ファイル）
```

**`#準備` が `#収録` より先**なのは、準備セッションが未整備の検知だけを行い、収録はその結果を受けて別セッションで走るという依存があるため（準備の中で収録を実行しない）。

レース単位のループの外側に、n=10単位で回る工程が2つある。

| 入口 | タイミング | 内容 | 担当 |
|---|---|---|---|
| `#集計` | 随時・n=10単位 | validate → analyze → backtest | Sonnet |
| `#設計` | n=10到達／開催替わり | 較正レビュー・rules_master改訂・工程変更 | Opus |

⑤の結果追記だけは起動フレーズを持たない工程で、`#更新` の後・`#振り返り` の前に必ず挟まる（記憶からの転記は禁止・一次ソース確認が条件）。

## 使い方

### 1. Claude.ai プロジェクト（現在の主運用）

1. Claude.ai でプロジェクトを作成し、本リポジトリを **GitHub Sync** でナレッジに接続する
2. `プロジェクト指示_v2.md` の内容をプロジェクト指示に貼る
3. チャットで **起動フレーズ**（`#準備` / `#収録` / `#予想` / `#更新` / `#振り返り` / `#集計` / `#設計`）で依頼する → 該当する工程セットが走る（冒頭に起動ヘッダ＝手順ファイル版数＋工程チェックリストが出る）
4. Claudeはログ追記行を**コードブロックで出力**する（Syncは読み取り専用のため）。ユーザーがローカルでCSVに追記 → commit → プロジェクト側で **Sync now**
5. 結果確定後は `#振り返り <レース名>` → references/振り返り手順.md のV0〜V7で層別採点・反実仮想・教訓ルーティングまで実行される（V4.5・V6.5はチェックリスト上の独立行）。V6.5でレース単位の回顧mdが `reflection/` に出力される
6. n=10到達時のレビューや閾値・係数の改訂判断は「較正レビュー」「設計セッション」で開始 → `ロードマップ_Opus運用設計_v1.md` の該当Phaseに沿って進める（担当はOpus。週次の予想実行とは分離）

### 起動フレーズ（入口の固定）

自由文の起動は工程の取りこぼしを生むため、依頼は7種のフレーズに固定する。書式と再評価範囲の定義は `プロジェクト指示_v2.md`「起動フレーズ」節が正本。ライフサイクル上の位置は前節の①〜⑥に対応する。

| フレーズ | 用途 | 必須の添え書き |
|---|---|---|
| `#準備 <対象週>` | ①週初1回。対象レース確定・予算宣言・未整備の検知（予想には入らない） | 前提（未コミット事項／較正カウンタ／未判断の論点） |
| `#収録 <コース or レース名>` | ②ナレッジ収録C0〜C6。枠順不要・別チャット | 種別（コース補正表／レース別傾向／血統D節／騎手C節／配当レンジ） |
| `#予想 <レース名>` | ③枠順確定後の本予想（工程0〜12を1応答で完走） | 枠順／予算／方向性／オッズ／馬場材料 |
| `#更新 <レース名>` | ④馬場・オッズ・馬体重の反映 | 確定事項＋**再評価範囲**（係数のみ／係数＋紐／全面） |
| `#振り返り <レース名>` | ⑥結果確定後のV0〜V7 | 結果ソース／実購入と計画の差異 |
| `#集計` | validate→analyze→backtest | — |
| `#設計` | 較正レビュー・台帳改訂・工程変更 | — |

`#更新` の**再評価範囲**が今の運用の要。宣言した範囲を超えて買い目を組み替えるのはロック違反（R08）として扱い、範囲外が必要な場合はClaudeが実行せず差し戻す。`#予想` は1回、`#更新` は当日最大2回。

### 2. Claude Code（リポジトリ直接編集）

スキル定義はリポジトリ内の `.claude/skills/keiba-prediction/SKILL.md`（本リポジトリで作業する限りそのまま発動する）。他プロジェクトからも使う場合は、そのファイルを含むディレクトリをスキルパスに置く：

```bash
# 全プロジェクト共通で使う場合（リポジトリを clone し、スキルディレクトリを参照させる）
git clone https://github.com/atoyr/keiba.git ~/src/keiba
cp -r ~/src/keiba/.claude/skills/keiba-prediction ~/.claude/skills/
```

※スキル本体は**ルーター**であり、工程・ゲートの正本は同リポジトリの `プロジェクト指示_v2.md` を都度読む前提。リポジトリから切り離したコピー単体では動かない。

配置後は「（レース名）の予想」等でスキルが発動し、手順は同じ `プロジェクト指示_v2.md` を読む。Claude.aiとの違いは1点だけ：**ログ追記・ナレッジ更新をClaudeがファイルへ直接行える**（コードブロック出力→手動転記が不要になる）。コミット＆pushは内容確認のうえユーザーがスキルディレクトリ内で行う（＝リポジトリの作業コピーがそのままスキル）。

### 3. 集計・バックテスト（n=10単位）

```bash
bash tools/claude_run.sh            # GitHub最新mainを取得して validate + analyze + backtest を一括実行
KEIBA_LOCAL=1 bash tools/claude_run.sh   # 手元の作業コピーで実行
python3 log/validate.py             # 個別実行（CSVスキーマ検証。ERRORありなら終了コード1）
python3 log/analyze.py              # 個別実行（実際に買った結果の集計）
python3 log/backtest.py [--detail]  # 個別実行（別戦略のリプレイ）
```

- **validate.py**：ログCSVの機械検証。[ERROR]＝ゲートFAIL級（この状態で予想・買い目を確定しない）、[WARN]＝記録不備。claude_run.sh の先頭でも実行され、ERROR検出時は後続集計を参考値扱いにする（R22）
  - スキーマ・数値ゲート・印の頭数（R15）・積み上げ検算・点数×単価（R16）に加え、**宣言と実装の突合**を行う：①荒れ度帯域と券種構成・堅実穴比の宣言タグ整合、②計画総額と実購入額の乖離（券種欠落の検出）、③rule_fires の `as_of=` と確定馬場の鮮度。タグ書式は `log/README.md` が正本
  - 「自己検証はプロンプトでなく機械チェックに置く」方針のため、応答内での再計算宣言は行わない（`プロジェクト指示_v2.md`「実行品質」節）
- **analyze.py**：印別複勝率・回収率、R値帯別成績、ルール遵守状況、ベースライン比較、r_adj分離
- **backtest.py**：印別・R帯別の単勝/複勝ベタ買いROI、三連単フォーメーション頭◎のみ vs ◎○両置きの比較（R12検証）、三連複 軸流し vs BOX。複勝ROIは place_odds_max による**上限推定（楽観値）**
- **Claude.aiのチャットから直接実行できる**：「集計して」「バックテスト実行」でClaudeがコード実行環境からGitHub最新mainを取得して実行する（ナレッジSyncとは別ルート・Sync now不要）
- 閾値・係数の見直しはこの集計を根拠に行い、n不足での再調整はしない（n<10は参考値）
- 予想・振り返り・集計セッションの冒頭は、Claudeが依頼なしで最新main取得→validate→正本同期チェックを行う（指示の「自動トリガー」節）

### 4. 情報収集（相手サイトに負荷をかけない）

```bash
python3 tools/polite_fetch.py <URL> [--ttl 秒] [--out file] [--data "cname=..."]
```

キャッシュ最優先（TTL内は実アクセスなし）・ホスト単位の最小間隔8秒＋1日60回上限・robots.txt遵守・429/503はRetry-After遵守。**403等の取得拒否は回避せず撤退**し、動作実績のある代替ソース（Yahoo競馬denma / netkeiba / 競馬ラボ）へ切り替える方針。`--data` はPOST遷移用（JRA公式の `/JRADB/*.html` はサイト本来の正規遷移がPOST。bot判定の回避ではない）。ローカル/Claude Code専用（Claude.aiの実行環境は外部サイトへ出られないため、Claude.ai内の取得は従来どおりweb検索）。

#### レース結果（JRA公式・一次ソース）

```bash
python3 tools/jra_result.py --index                            # 取得可能な開催日を一覧
python3 tools/jra_result.py --date 2026-08-02 --course 札幌 --race 11
python3 tools/jra_result.py --date 2026-08-02 --course 札幌 --race 11 --json
```

着順（タイム・着差・通過順・上り3F・馬体重・人気）／**ハロンタイム**／コーナー通過順位／全券種の配当／天候・**発表馬場**をJRA公式から構造化して取得する。振り返り（V0事実確定）の一次ソースはこれを使う。

- CNAME 末尾はサイト側のチェックサムでURLを自前生成できないため、必ず開催選択ページから辿る（推測でURLを組み立てない）
- JRA公式の開催選択は**直近2か月程度しか収録しない**。範囲外の日付は収録範囲を示して「取得失敗」で終了する
- **含水率・クッション値は結果ページに無い**（別の「馬場情報」ページ・開催中のみ公開）。本ツールは出力しないので、推測で埋めず取得失敗として扱う
- 2026-08-02 検証：`www.jra.go.jp` の robots.txt は全面許可、正直なUAで 200。過去ログの「JRA公式はbot検出でブロック」は誤りで、原因は CNAME 遷移に到達できていなかったこと

## 運用の絶対原則（抜粋）

- **ルールゲートを通ってから買い目**。followed=0 が残る状態で印・買い目を確定しない
- **数値列が埋まっていない predictions.csv はゲートFAIL扱い**（オッズ未確定のR値・r_adjのみ暫定可）
- **検算ゲート**：predictions.csv の最終点は base×合成係数＋加算 の再計算と一致していること（裁量調整は calc_gap として理由を明記）
- **反証パス**：印確定前に◎○の不成立シナリオを確認する。反証単独での格下げは不可。独立検証は『予想評論_エージェントルール.md』を別チャットで
- **荒れ度はベース点に触れない**（買い目配分・閾値・頭固定判断にのみ作用）
- **結果はJRA公式を検索して確認**。チャット記憶からの転記は禁止
- **不明は不明のまま**。データ取得失敗を推測で埋めない
- **新しい失敗則・閾値は指示ファイルでなく rules_master.csv と該当ナレッジへ追記**（指示の改訂は工程・ゲート構造が変わるときのみ）
- **三点同期**：工程・ディレクトリ構成・実行方法を変える変更では、`プロジェクト指示_v2.md`・`README.md`・`SKILL.md` を同じコミットで更新する。指示だけ直してREADME/SKILLが古いままの状態を作らない
